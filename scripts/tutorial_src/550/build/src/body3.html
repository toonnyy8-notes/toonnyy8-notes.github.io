10 · 失敗與發現

失敗嘗試與關鍵發現

驗證器（App. G.1）。R1-Zero 的效果高度依賴獎勵訊號是否可靠。作者目前的經驗是，規則式獎勵與「以 LLM 對照標準答案判斷對錯」兩種方式能減輕 reward hacking；後者適合答案簡短明確的任務，不容易推廣到開放生成與長文寫作。

迭代流程（App. G.1）。RL 讓模型探索人工標註達不到的推理軌跡；SFT 處理難以定義可靠獎勵的任務，例如開放問答與創意寫作。只用 RL 會在定義不良的任務上 reward hacking，只用 SFT 則無法透過探索最佳化推理，所以作者認為兩者都不可缺少。

過程獎勵模型（process reward model, PRM）的三個限制（App. G.2）。PRM 對推理的每一步打分。作者列出：一般推理中難以明確定義「一步」；難以判斷中間步驟是否正確，自動標註效果不佳、人工標註又難以擴展；一旦引入模型式 PRM，必然導致 reward hacking，重新訓練又增加資源與流程複雜度。PRM 在重排前 N 個回應或引導搜尋上有用，但相對於大規模 RL 的額外成本，優勢有限。

蒙地卡羅樹搜尋（MCTS）的兩個挑戰（App. G.2）。作者仿照 AlphaGo 與 AlphaZero，把答案拆成小段做樹搜尋，並以預訓練的價值模型引導。但 token 生成的搜尋空間比西洋棋大上指數倍，限制每個節點的最大擴展數又可能陷入局部最佳；價值模型直接影響每一步搜尋的品質，而細粒度的價值模型很難訓練，無法像 AlphaGo 那樣逐步自我改進。作者的結論是，MCTS 搭配預訓練價值模型可以改善推論，但以自我搜尋反覆提升模型仍很困難。

reward hacking 實例（App. B.5、Fig. 6）。以有用性獎勵模型訓練時，獎勵分數持續上升，但 CodeForces 的 test pass@1 下降。這是第二階段 RL 只在最後 400 步加入偏好獎勵的原因。

延伸閱讀：過程監督與 PRM：結果與步驟回饋的比較

檢查理解

PRM 有哪三個限制？MCTS 遇到哪兩個挑戰？

PRM：「一步」難定義、中間步驟對錯難判斷、模型式 PRM 必然被 reward hacking。MCTS：搜尋空間比西洋棋大上指數倍、細粒度價值模型難訓練（App. G.2）。

基礎設施（App. B.1）。RL 框架分成四個模組：Rollout（以 vLLM 取樣；MoE 跨節點專家平行、熱點專家冗餘，並以多 token 預測做自我推測解碼）、Inference（獎勵模型與參考模型的前向計算）、Rule-based Reward（程式執行器、答案比對、格式檢查，以非同步排程與前兩者重疊）、Training（依長度排序後以 Best-Fit 打包成固定長度區塊，並用 DualPipe 管線平行）。除規則獎勵模組外，每個模組結束後把模型從 GPU 記憶體卸載到主記憶體或磁碟。

成本（App. B.4.4、Table 7，以 H800 每 GPU 小時 2 美元計）。R1-Zero 用 64×8 張 H800 約 198 小時，共 101K GPU 小時（202K 美元）；SFT 資料製作 5K GPU 小時（10K 美元）；R1 約 80 小時，41K GPU 小時（82K 美元）；合計 147K GPU 小時、294K 美元。$64\times8\times198=101{,}376$、$64\times8\times80=40{,}960$，與表一致本頁推導。

常見錯誤

  1. 以為 R1 完全沒有 SFT：只有 R1-Zero 沒有 SFT；R1 有冷啟動 SFT 與 80 萬筆的第二次 SFT（Sec. 3、App. B.4.2）。
  2. 以為 Dev3 由 Dev2 繼續微調：第二次 SFT 微調的是 DeepSeek-V3-Base，Dev2 只用來拒絕取樣產生資料（App. B.4.2、B.3.3）。
  3. 全對或全錯的群組照算 Eq. 3：std = 0，需要保護；這些題目沒有獎勵訊號，只剩 β > 0 時的 KL 梯度本頁推導。
  4. 期待格式獎勵在所有輸出都合規時仍有作用：常數獎勵不改變優勢本頁推導。
  5. 沿用 PPO 原論文常用的 ε = 0.2（本文未使用此值）：R1 第一階段 RL 用 ε = 10，此時負優勢一側的裁剪不會啟動。
  6. 把 KL 懲罰加在每個 token 的獎勵中（PPO 做法）：GRPO 加在損失中；前者可能隱含懲罰長度（App. A.3）。
  7. 以 greedy decoding 評測長推理模型：論文改用溫度 0.6、top-p 0.95 的 pass@1（App. D.1）。
  8. 在小模型上直接複製純 RL：7B dense、16B MoE 沒有成功（App. G.1）；小模型用蒸餾較好（App. F.1）。
  9. 在偏好獎勵上訓練太久：第二階段 RL 只在最後 400 步加偏好獎勵，更多步會 reward hacking（Sec. 3.2.2、App. B.5）。
  10. 用 few-shot 提示評測或使用 R1：few-shot 一致降低表現，建議 zero-shot 直接描述問題與輸出格式（Sec. 6、App. D.1）。

12 · 安全與限制

安全評估與限制

安全（App. D.3）。官方服務另有風險控制系統：使用者問題先比對關鍵字，命中者連同 Listing 8 的審查提示送給 DeepSeek-V3 判斷是否撤回回應。Table 9 六個公開安全基準的平均分數，R1 為 95.0，括號內的模型本身分數為 85.9。Table 11 的越獄攻擊中，R1（無風控）的不安全比例由 25.2% 升到 85.9%；加上風控後不安全比例為 4.3%，拒答比例 87.3%。50 種語言的安全分數，R1 加風控為 85.9%、模型本身為 74.2%（D.3.4）。85.9 在這三處分別是不同的指標。作者建議部署開源模型的開發者採用類似的風控（D.3.5）。

能力限制（Sec. 6）。結構化輸出與工具使用較弱；簡單問題仍有過度思考，token 效率有改進空間；針對中英文最佳化，其他語言的問題可能以英文推理或回答；對提示敏感，few-shot 會降低表現；軟體工程任務評估時間長，沒有大規模 RL，相對 DeepSeek-V3 提升有限。

方法限制（Sec. 6）。純 RL 依賴可靠的獎勵訊號；寫作等任務難以建構可靠的獎勵模型，以模型打分時容易被利用。對無法可靠評估的複雜任務，擴展純 RL 仍是開放問題。

檢查理解

R1（無風控）在越獄攻擊下的不安全比例如何變化？作者列出哪一項方法層面的限制？

25.2% 升到 85.9%（Table 11）；純 RL 依賴可靠獎勵，無法可靠評估的任務上擴展純 RL 仍是開放問題（Sec. 6）。
